# Learn from PRDs without inheriting their mistakes

Use only when the user asks to learn a writing style or when a source conflict affects the current PRD. Ordinary drafting loads the active Profile and, if needed, one relevant sample—not the whole archive.

## Establish what each source proves

Keep a compact source map with the document/version, provenance, approval evidence, and role:

- A user-supplied original is evidence of that document's writing, not automatic endorsement of every clause.
- A user-approved revision demonstrates only what the user approved: structure, density, wording, or product decisions may have different approval scopes.
- A discovered local draft has unknown authorship/approval unless there is evidence otherwise. Do not call it the user's golden example.
- A memory summary is a secondary account. Do not claim to have reread its original.
- A generic fixture is an instructional example, not a user's preference or product truth.

Group versions of the same requirement as one sample family. Three revisions do not demonstrate three independent preferences. File dates and version names do not establish approval or current product scope. If an original is missing, request its title/link/file and state which conclusions remain provisional; do not stop unrelated work or invent the source.

## Extract patterns, not a universal template

Compare what makes review easier: how the problem is framed, where the journey starts, how scenes specify actions and fields, how examples explain rules, and how limitations are attached to behavior. Separate:

| Finding | Treatment |
| --- | --- |
| Explicit current writing preference | Apply within its stated scope; preserve compatible older guidance. |
| Pattern shared across distinct approved examples | Candidate stable preference; retain examples and applicability. |
| One document's special chapter or domain rule | Conditional technique, not a mandatory chapter or future product fact. |
| Old guidance contradicted by a newer explicit correction | Retire that guidance; do not keep both rules active. |
| Product scope differs and authority is unclear | Surface the choice; never silently combine both versions. |
| Technical detail mixed into an otherwise useful sample | Retain its product consequence, not the implementation prescription. |

For example, a data-heavy document can benefit from coverage and metric tables; that does not make data requirements necessary for a simple navigation change. A worked conversation can illustrate an experience; it must not dictate a model's exact answer format. A business threshold belongs in the PRD only when it is a real product decision, not because an old sample used that number.

## Learn from counterexamples too

Watch for a complete journey that promises more than the stated release scope, a capability table that disagrees with the example, or a “shorter” revision that removes essential rules. Translate technical constraints into human-visible boundaries—for example, explain that some data is unavailable and how the user proceeds, without prescribing a service or storage design.

Only propose changes supported by available evidence. Keep a brief rationale and any uncertainty outside the PRD itself. On authorized Profile maintenance, create a versioned, private update; do not upload personal examples, silently install the Skill, or claim a new Profile proves host loading.
