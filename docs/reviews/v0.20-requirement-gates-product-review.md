# v0.20 需求级角色门禁 · 产品逻辑审查

## v0.20.0 · 2026-08-23 · 开发前产品逻辑审查

### 审查对象

- 需求范围：`task-178`–`task-183`。
- 用户目标：每条需求独立经历产品审查、开发交付和 QA 验证；不能由一次 Plan 或一条角色事件跳过关键节点。
- 审查深度：Deep。该能力会决定所有项目的角色状态和后续开发权限，错误状态可能跨项目扩散。

### 模拟路径

1. PM 明确需求并提交审查；Reviewer 发现取消后的状态未定义，需求返回 PM，开发不能开始。
2. Reviewer 批准后，普通需求进入开发；复杂需求先进入 Planner / Designer，再进入开发。
3. Executor 声称完成但没有产物或自检证据，需求继续停在开发；证据齐全后才进入 QA。
4. QA 在开发交付前直接回写“通过”，事件保留但不推进；开发交付后，QA 有独立证据才进入发布准备。
5. 高风险需求在 QA 通过后进入发布审查；普通需求不重复增加 Reviewer 环节。
6. 已批准需求发生用户行为、权限、持久状态或恢复逻辑变化，旧批准失效并重新回到产品审查。
7. 纯技术缺陷不改变产品行为时，记录例外原因并保留开发产物、自检和 QA，允许跳过产品审查。

### 已解决的阻塞发现

- Reviewer 同时承担开发前和发布前审查容易混淆：已使用 `product_review` / `release_review` 明确区分，缺少模式不能给门禁结论。
- 版本级角色会掩盖逐需求差异：已改为每个 `requirement_id` 独立投影，版本完成比例不再决定角色阶段。
- 自由文本可伪造进度：已改为结构化门禁结果和证据引用；非法跳转进入审计，不改变有效阶段。
- Executor 自验与 QA 独立验收混为一谈：已要求开发交付同时提供产物和自检，QA 另行提供独立证据。

### 非阻塞剩余风险

- “纯技术、不改变产品行为”仍需要角色做语义判断，后端只能强制记录原因和证据，不能完全自动证明该判断正确。
- 范围变化只有在 PM 回写新的 `ready_for_review` 时才会使旧批准失效；未来可增加文件/需求摘要变化提示，但不应让哈希自动替代产品裁决。
- 历史事件没有新门禁字段，只保持旧版可读，不反向推断为已通过产品审查。

### 不变量与结论

- 产品逻辑未批准，产品行为需求不能进入开发。
- 开发没有产物与本轮自检，不能进入 QA。
- QA 没有独立证据，不能进入发布准备。
- 任一非法事件可追踪但不能推进有效阶段。
- 每条需求独立运行，不允许其他需求或版本总进度代替本需求证据。

`gate_result=approved`。可以继续实现与 QA；上述剩余风险保留到发布 Review 核对。
